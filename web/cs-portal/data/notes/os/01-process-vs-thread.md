# 进程与线程：一次把概念理清楚

「进程是资源分配的基本单位，线程是调度的基本单位」——这句话背过很多遍。但真正需要想清楚的是：**为什么要分成两层？合成一层不行吗？**

## 从"合不来"说起

假设只有进程，没有线程。现在一个程序要做两件事：一边接收用户输入，一边在后台算一个大任务。

进程之间是隔离的，内存不共享。于是：

- **方案 A：开两个进程。** 算大任务的那个进程想用输入进程收到的数据？只能靠进程间通信（管道、共享内存、socket），要序列化、要拷贝、要处理同步。
- **方案 B：一个进程轮流做两件事。** 那输入就会卡住，用户体验很差。

两个方案都不舒服。问题的根源是：**这两件事本来就应该共享同一份数据、同一段代码，但需要能被独立调度。**

于是有了线程。

## 拆开看：各自负责什么

| | 进程 | 线程 |
|---|---|---|
| 拥有什么 | 独立的地址空间、文件描述符、信号处理 | 只有**栈**和**寄存器**，其余全部共享 |
| 切换成本 | 高（要换页表、刷 TLB） | 低（同一地址空间内） |
| 通信方式 | 需要 IPC 机制 | 直接读写共享变量 |
| 崩溃影响 | 互不影响 | 一个线程崩了，整个进程挂掉 |

看这张表就明白了：**进程提供隔离，线程提供并发。**

一个进程里的多个线程共享：代码段、数据段、堆、打开的文件。各自独有：**栈、程序计数器、寄存器**。

所以「线程是调度的基本单位」的意思是：CPU 调度的对象是线程，不是进程。操作系统看着一堆线程在跑，根本不知道哪个属于哪个进程。

## "共享"带来的代价

线程模型最大的好处是共享内存，最大的麻烦也是共享内存。

```python
# Python 里一个经典陷阱
counter = 0

def increase():
    global counter
    for _ in range(100000):
        counter += 1
```

开两个线程分别跑 `increase()`，直觉上是 200000，实际跑出来经常是 15 万上下。

原因：`counter += 1` 不是原子的，它其实是三步——

1. 读 `counter` 到寄存器
2. 寄存器加一
3. 写回 `counter`

两个线程可能同时读到 5，各自加一，各自写回 6，一次增加就这么丢了。这叫**竞态条件**。

解法是加锁：

```python
import threading
lock = threading.Lock()
counter = 0

def increase():
    global counter
    for _ in range(100000):
        with lock:          # 同一时刻只有一个线程能进
            counter += 1
```

但锁又带来新问题：**死锁**。两个线程各持一把锁，又都在等对方的锁，就永远等下去了。

## 一个常见的误解

「多线程一定比单线程快」——不对。

线程的价值在于**让 CPU 在等 I/O 的时候别闲着**。如果一个任务是纯计算的，开 4 个线程在 4 核上跑，理论最快也就是 4 倍；但在 1 核机器上，反而因为切换开销变慢。

所以：

- **I/O 密集型**（网络请求、读写文件）→ 多线程收益明显
- **计算密集型**（大量数学运算）→ 多进程更合适（Python 里更明显，因为有 GIL）

## Python 的 GIL 是怎么回事

CPython 有个全局解释器锁（GIL）：**同一时刻只有一个线程能执行 Python 字节码。**

这意味着 Python 的多线程在计算密集场景下几乎没收益——4 个线程也没法真正并行跑 Python 代码。

但注意 GIL 在两种情况下会释放：

1. **I/O 阻塞时**（发起网络请求、读文件）→ 所以多线程做爬虫依然有效
2. **调用 C 扩展时**（NumPy 的矩阵运算）→ 所以 NumPy 内部是能真并行的

这也解释了为什么数据科学里 NumPy 这么重要：它把重活丢给了 C 层，绕开了 GIL。

## 自测

1. 线程共享什么、独有什么？——共享地址空间与文件，独有栈和寄存器。
2. 为什么进程切换比线程切换贵？——要换页表、刷新 TLB，缓存局部性也被破坏。
3. I/O 密集和计算密集分别该用什么？——前者多线程/异步，后者多进程。
4. 竞态条件的本质是什么？——"读—改—写"不是原子操作，中间被插队。
