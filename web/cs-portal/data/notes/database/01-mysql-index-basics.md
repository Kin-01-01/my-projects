# MySQL 索引：为什么加了索引就能快这么多

一句话版本：索引把「一行一行翻」换成了「按树跳着找」。代价是要多存一份结构、写入要额外维护。

## 先说一个具体的场景

假设有这样一张表，两百万行：

```sql
CREATE TABLE orders (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT      NOT NULL,
  status      TINYINT     NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  created_at  DATETIME    NOT NULL
);
```

现在执行：

```sql
SELECT * FROM orders WHERE user_id = 10086;
```

**没有索引**时，MySQL 只能从第一行开始逐行读出 `user_id` 去比对。两百万行就是两百万次读取，磁盘 I/O 直接爆掉。这叫**全表扫描**，`EXPLAIN` 里 `type` 显示为 `ALL`。

**加上索引**：

```sql
CREATE INDEX idx_user_id ON orders(user_id);
```

同样的查询，`EXPLAIN` 的 `type` 变成 `ref`，扫描行数从 2000000 掉到个位数。快几百倍的原因只有一个：**它不再逐行看了**。

## 为什么 B+ 树能做到"跳着找"

核心是它的两个特征：

1. **每一层都是有序的**，所以可以用二分的思想快速定位到下一层的入口；
2. **每个节点能放很多个键**（一个页 16KB，放几百个键没问题），所以树的**层数很低**。

这点常被忽略。两百万行数据，一棵 B+ 树大概只有 **3 层**。也就是说，一次等值查询最多读 **3 个页**——根节点通常还常驻内存，实际可能只有 1~2 次磁盘 I/O。

对比一下二叉搜索树：两百万个节点，树高约 21 层。同样查一次，要多跑十几次 I/O。**B+ 树赢在"矮"**，不在"二分"。

## 一个容易搞混的点：聚簇索引 vs 二级索引

InnoDB 里，索引分两种：

| | 聚簇索引（主键索引） | 二级索引（普通索引） |
|---|---|---|
| 叶子节点存什么 | **完整的行数据** | 主键值 |
| 一张表有几个 | 有且只有一个 | 可以有多个 |
| 查询要回表吗 | 不需要 | **通常需要** |

所以下面这条查询：

```sql
SELECT * FROM orders WHERE user_id = 10086;
```

实际走了**两步**：

1. 在 `idx_user_id` 这棵树上找到 `user_id = 10086` 的记录，拿到主键 `id`；
2. 再拿这个 `id` 去聚簇索引里捞出整行——这一步叫**回表**。

如果只查主键本身：

```sql
SELECT id FROM orders WHERE user_id = 10086;
```

第二步就省了，因为二级索引的叶子节点里已经有 `id`。这叫**覆盖索引**，是常用的优化手段：

```sql
-- 把要查的列直接放进索引，彻底避免回表
CREATE INDEX idx_user_status ON orders(user_id, status);
SELECT user_id, status FROM orders WHERE user_id = 10086;
```

## 最左前缀：复合索引的钥匙

复合索引 `(a, b, c)` 的排序规则是：**先按 a 排，a 相同再按 b 排，b 相同再按 c 排**。

这就决定了它能被怎么用：

| 查询条件 | 能用上索引吗 |
|---|---|
| `WHERE a = 1` | 能 |
| `WHERE a = 1 AND b = 2` | 能 |
| `WHERE a = 1 AND b = 2 AND c = 3` | 能 |
| `WHERE b = 2` | **不能** |
| `WHERE a = 1 AND c = 3` | 只能用到 `a` |

道理很简单：整体是按 `a` 排序的，你跳过 `a` 直接找 `b`，那还是乱序的，只能扫全表。

还有一个细节：**范围查询会截断后面的列**。

```sql
-- 只能用上 a，b 用不上
SELECT * FROM t WHERE a > 1 AND b = 2;
```

因为 `a > 1` 这个范围内，`b` 是不保证有序的。

> 所以复合索引的列顺序不是随便排的：**等值条件在前，范围条件在后**。

## 索引不是越多越好

索引的代价有三块：

- **占空间**：B+ 树本身要存，一个二级索引就是一棵独立的树；
- **拖慢写入**：每插一行，所有索引都要跟着调整位置；
- **可能选错**：优化器有时会挑一个不该用的索引。

第三种情况的典型表现是：**明明有索引，却更慢了**。比如 `WHERE status = 1`，如果全表 90% 的行 `status` 都是 1，那走索引要先定位、再逐行回表，还不如直接全表扫描来得快。这时候 `EXPLAIN` 里 `rows` 很大、`type` 是 `ALL`，其实是优化器"故意"不用索引。

## 我现在的排查顺序

遇到慢查询，按这个顺序看：

1. `EXPLAIN` 看 `type` —— 出现 `ALL` 就是全表扫描；
2. 看 `key` —— 是不是 `NULL`，或者用错了索引；
3. 看 `rows` —— 估算扫描行数，跟结果行数差多少；
4. 看 `Extra` —— 出现 `Using filesort` / `Using temporary` 基本都要优化。

## 自测

1. 为什么 B+ 树比二叉搜索树更适合做数据库索引？——因为它矮，I/O 次数少。
2. 二级索引查到主键之后还要做什么？——回表，去聚簇索引捞完整行。
3. 复合索引 `(a, b, c)` 上，`WHERE b = 1` 能用上索引吗？——不能，不满足最左前缀。
4. 为什么有索引有时反而更慢？——选择性太差时，回表成本超过全表扫描。
