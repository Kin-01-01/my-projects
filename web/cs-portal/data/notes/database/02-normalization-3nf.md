# 数据库范式：从插入异常讲到第三范式

直接背「1NF 列不可分、2NF 消除部分依赖、3NF 消除传递依赖」记不住也用不上。换个顺序：**先看坏设计会出什么问题，再看范式是拿来治什么病的。**

## 一张有问题的表

假设要记录学生选课：

| 学号 | 姓名 | 课程 | 学分 | 教师 | 教师办公室 |
|---|---|---|---|---|---|
| 1001 | 张三 | 数据库 | 3 | 王老师 | A301 |
| 1001 | 张三 | 操作系统 | 4 | 李老师 | B205 |
| 1002 | 李四 | 数据库 | 3 | 王老师 | A301 |

看着还行？实际用起来有四个坑：

**1. 插入异常**
新开了一门「编译原理」，但还没有学生选。想把它记进表里？没法记——主键是（学号，课程），学号不能为空。

**2. 更新异常**
王老师的办公室从 A301 搬到 A302。这张表里有两条王老师的记录，得全改。**改漏一条，数据就不一致了。**

**3. 删除异常**
1002 号学生退了数据库课，这一行删掉之后，「数据库课 3 学分、王老师教」这条信息也跟着没了。

**4. 数据冗余**
「数据库」「3 学分」「王老师」「A301」这些信息被重复存了很多遍。

根源是同一个：**非主键字段之间存在不该有的依赖关系**。

## 第一范式（1NF）：字段不可再分

最基础的一条：**每一列都是原子值，不能再拆。**

反例——把两门课塞进一格：

| 学号 | 课程 |
|---|---|
| 1001 | 数据库, 操作系统 |

问题在于：想统计「选了数据库的学生有几个」，得对字符串做模糊匹配。`WHERE 课程 LIKE '%数据库%'` 还会误伤「数据库原理」。拆成两行就好了。

> 注意：1NF 关心的是「一个格子能不能装两个值」，不是「一个格子该不该装两个值」。

## 第二范式（2NF）：消除部分依赖

前提是 1NF，然后要求：**非主键列必须完全依赖于整个主键，不能只依赖主键的一部分。**

上面那张表主键是（学号，课程），而：

- `姓名` 只依赖 `学号` → **只依赖主键的一部分**，违反 2NF
- `学分` 只依赖 `课程` → 同样违反

拆开：

```
学生表(学号 PK, 姓名)
课程表(课程 PK, 学分)
选课表(学号, 课程, 成绩)   -- 主键是(学号,课程)，两个非主键列都完整依赖它
```

> 如果主键本身就是单一列（比如 `id`），那 2NF 自动满足——不存在「主键的一部分」这个概念。

## 第三范式（3NF）：消除传递依赖

在 2NF 基础上要求：**非主键列不能依赖另一个非主键列。**

前面那份数据里，`教师办公室` 依赖 `教师`，而 `教师` 又不是主键——这就是**传递依赖**：`学号 → 教师 → 教师办公室`。

再拆一层：

```
教师表(教师工号 PK, 姓名, 办公室)
课程表(课程 PK, 学分, 教师工号 FK)
```

到这里，每个非主键字段都只依赖主键，没有传递，3NF 达标。

## 一句总结

| 范式 | 要求 | 治的病 |
|---|---|---|
| 1NF | 列不可再分 | 一格塞两个值，查询没法用 |
| 2NF | 非主键列完全依赖主键 | 部分依赖导致冗余与更新异常 |
| 3NF | 非主键列之间不能相互依赖 | 传递依赖导致冗余与更新异常 |

**判断口诀**：把表的主键写下来，然后对每一个非主键列问一句「它到底依赖谁」。

- 依赖主键的一部分 → 违反 2NF
- 依赖另一个非主键列 → 违反 3NF
- 完整且只依赖主键 → 合格

## 但别教条

范式不是越高越好。实际项目里，**读多写少的报表场景经常故意反范式**——把 `教师姓名` 冗余进课程表，省掉一次 JOIN。

判断标准不是「满足第几范式」，而是：**这张表主要被谁用、怎么用。** 写多、要一致，就规范；读多、要快，可以适度冗余，但要接受维护冗余的成本。

考试里按范式答，工程里按场景选。
